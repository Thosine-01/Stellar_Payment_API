# Dashboard localization (i18n)

Issue #428. The merchant dashboard is localized with `next-intl`. It uses
cookie-based locale selection, so URLs carry no locale prefix.

## Supported locales

| Code | Language | HTML `lang` |
|------|----------|-------------|
| `en` | English (default, source of truth) | `en-US` |
| `es` | Spanish | `es-ES` |
| `pt` | Portuguese | `pt-BR` |
| `fr` | French | `fr-FR` |

The list lives in `src/i18n/config.ts` (`locales`). Routing, the request config
and the header switcher all read it.

## How the locale is chosen

1. `LocaleSwitcher` in the authenticated dashboard header writes the `NEXT_LOCALE` cookie (1 year, `SameSite=Lax`) and calls `router.replace` on the current route, keeping the query string.
2. `src/i18n/request.ts` reads the cookie on the server, validates it with `resolveAppLocale()` (unknown values fall back to `en`), and loads `messages/<locale>.json`.
3. `ThemeLanguageSync` updates `<html lang>` using `localeToLanguageTag()`.

## Adding or changing strings

- Add the key to `messages/en.json` first, then to `es.json`, `pt.json` and `fr.json` under the same path.
- Use `useTranslations("<namespace>")` in components. Do not hard-code user-facing English in dashboard components; that includes `aria-label`s.
- Keep ICU placeholders identical across locales (`{count}`, `{asset}`, plural blocks).

`src/i18n/messages.test.ts` enforces this. It fails if any locale is missing a
key, has an extra key, drops an ICU argument or contains an empty string.

## Adding a locale

1. Add the code to `locales` in `src/i18n/config.ts` and a case to `localeToLanguageTag`.
2. Create `messages/<code>.json` with every key from `en.json`.
3. Add `localeSwitcher.options.<code>` to every catalogue.
4. Run `npm run test:unit -- src/i18n src/components/LocaleSwitcher.test.tsx`.
